# STORY-11.1 fix plan — Objectives UI — coach set, player view

> **Status today:** DONE (tracker) — Home preview card wiring, team-manager read-only access, and player self-authored objectives all implemented and tested; suggestions latency remains deferred to STORY-11.2 (see Fix plan item 4). The "self-authored objectives" decision was reversed mid-implementation: originally deferred as post-MVP, then explicitly un-deferred and scoped to **players only** (Team Manager stays read-only, unchanged). Tracker `status` was never actually flipped off DONE (no BUG-QA3-01/02/07 entries exist in `docs/index.html`'s `bugs` array), so `verify.tests`/`verify.files`/`audit_notes` were updated instead of a status flip.
> **QA evidence:** docs/Coach_Feedback.docx (coach, player, and team account sections)
> **Related:** docs/index.html (tracker), docs/bug-investigations.md (QA2-04, already resolved-as-explained, background only)

## What QA reported

- Coach: "Dashboard objectives no linked" / "Dashboard objectives not clickable" / "Where do I set the objectives?"
- Player (player/pro account): "Objectives not linked or clickable." / "Suggested objectives slow to load. Should be able to add my own as well."
- Team (team/pro account): "Pro activated, objectives on dash still say upgrade to pro."

## Acceptance criteria at risk

- **AC-1** "Coach at Pro sets objectives for individual players and teams" — not contradicted. `ObjectivesScreen` (`apps/mobile/src/features/objectives/ui/ObjectivesScreen.jsx:93,391,541`) gates the create form on `isCoach` and fetches/saves via `repos.objectives`. This works as designed; the coach complaint is about the **Home dashboard preview card**, not this screen (see Root cause).
- **AC-2** "Player at Pro views assigned objectives and progress rings" — **partially at risk**. `ObjectivesScreen` itself loads real data (`repos.objectives.listForUser(userId, role)`, `ObjectivesScreen.jsx:123`) and renders `ObjectiveProgressRing` for real rows — that part holds up. But the **Home screen's "Objectives" preview card**, which is what QA actually saw first, is hardcoded mock data for every role (see below), which is what "not linked" most likely refers to.
- **AC-4** "Objective schema supports player and team goals ... (details TBD post-MVP if needed)" — the "TBD post-MVP" clause directly covers QA3-02's "add my own" ask; see Open Questions.

## Root cause (confirmed in code)

1. **Home "Objectives" preview card is hardcoded for every role**, not just coach. `apps/mobile/src/App.jsx:386-411`:
   - Line 389: `{canAccess(user, "objectives") ? "Manage" : "Pro"}` — the header link.
   - Lines 391-404: when access is granted, the component renders a **literal hardcoded array** — `[{ n: "Improve 3PT %", p: 72, ... }, { n: "Defensive rotations", p: 45, ... }]` — not `repos.objectives` data, for coach, player, *and* team alike. This block is not branched by `isPlayer`/`isTeam` the way the "Upcoming" section above it (`App.jsx:355-383`) is.
   - The rendered mock cards also carry **no `onClick`** (lines 393-403) — only the "Manage" label (line 389) navigates to `ObjectivesScreen`. So even when unlocked, the preview cards themselves are inert, matching the "not clickable" complaint literally.
   - This is the same category of defect as the already-resolved-as-explained QA2-04 (coach Home stats/upcoming/objectives are mock data) — QA2-04's notes say "Player home progress/schedule is live," but that referred to the **Upcoming** section only; the Objectives preview card was never covered by that fix and remains fake for all roles.

2. **Team role is unconditionally denied the `objectives` feature regardless of tier — this is the real cause of QA3-07**, not a tier/bug in the access-check logic itself:
   - `packages/domain/src/subscription/paywall.ts:26`: `objectives: { coach: 'pro', player: 'pro' }` — **there is no `team` key**.
   - `packages/domain/src/rbac/launch-matrix.ts:110-156` (`resolveLaunchFeatureAccess`): for `feature: 'objectives', role: 'team'`, `LAUNCH_ACCESS_BANDS['objectives']` is undefined (not in that table, `launch-matrix.ts:52-76`) and `reqs['objectives']?.['team']` is `undefined`. Both being falsy hits `launch-matrix.ts:126-128`: `if (!band && !minFromMap) return { allowed: false, accessLevel: 'none', requiredTier: null }`.
   - `apps/mobile/src/App.jsx:84-92` (`canAccess`) calls this directly with `user.role` — for a team-manager account `user.role === "team"` (`App.jsx:175`), so `canAccess(user, "objectives")` is **always `false`**, independent of `user.tier`. That is exactly "Pro activated, objectives on dash still say upgrade to pro": the UI isn't mis-reading the tier, the feature is simply never granted to the `team` role at any tier today.
   - This is **not a STORY-5.2 defect** — STORY-5.2's own ACs (chat AC-1, AI AC-2, content-creation AC-3, ◎/○ bands AC-4, deferred-matrix AC-5) never mention `objectives`; the `objectives` row in `FEATURE_TIER_REQUIREMENTS` predates/sits outside that story's AC scope. **Resolved: STORY-5.2 does not get reopened** — once the team-objectives fix ships, add a new AC-6 to STORY-5.2 for traceability instead.
   - STORY-11.1's own title is literally "coach set, **player** view" — the AC-1 phrase "sets objectives for individual players and **teams**" is about the *target* of an objective (a team-wide goal), not about the Team Manager *role* being able to view the Objectives screen. **Resolved:** today's zero-access behavior is *not* intentional — Team Manager gets read-only access, scoped to team-wide objectives only (not individual players' objectives). See Fix plan item 2.

3. **No player-authored objectives (resolved — now built, players only)**: `ObjectivesScreen.jsx:391,541` gated the entire create/edit form on `isCoach` (`role === 'coach'`, line 93). This matched QA3-02's "should be able to add my own as well" complaint exactly. **New finding surfaced while implementing:** the UI gate was only half the story — the `objectives` table's `objectives_coach_insert` RLS policy (`supabase/migrations/20260723220000_objectives.sql:50-60`) requires `coach_id = auth.uid() AND profiles.role = 'coach'`, so a player could not have inserted a row even with a client-side form change. This needed a new, additive RLS policy (second permissive `for insert` policy, OR'd with the existing one), not just a UI change. See Fix plan item 3.

4. **Suggestions "slow to load" (QA3-02) — confirmed, not just plausible.** `loadSuggestions` (`ObjectivesScreen.jsx:135-185`) awaits `repos.marketplacePurchases.listOwned()` (line 147) *then* `repos.packageRecommendations.listRecommendations(...)` (line 164), which calls the `recommend-packages` Edge Function. That function (`supabase/functions/recommend-packages/index.ts:184,239-240`) makes **two sequential external Mistral API calls per request** when `aiConfig.llmRerankEnabled` is true: `await embedTextWithMistral(queryText)` (line 184), then `await rerankPackagesWithMistral(providerPayload)` (line 239-240). `llmRerankEnabled` defaults to `true` (`supabase/functions/recommend-packages/handler.ts:100-107`, `DEFAULT_AI_RECOMMENDATION_CONFIG`). Two sequential external LLM calls plus the client-side serial awaits is a fully sufficient, confirmed explanation for the reported slowness — no further measurement needed to establish *that* it's slow, only to quantify by how much.
   - **This directly contradicts STORY-11.2's own `audit_notes`**, which states "No RAG/LLM (11.3/11.4)" — see the STORY-11.2 fix plan for that discrepancy; it's out of this document's scope to resolve but it changes the fix (disable/short-circuit the LLM path vs. just reordering client awaits).

## Fix plan

1. **Wire the Home "Objectives" preview card to real data (implemented)**, for all three roles:
   - `App.jsx`'s `HomeScreen` now fetches `repos.objectives.listForUser(playerId, user.role)` via its own `loadHomeObjectives` effect (decoupled from the player-only session/completions fetch, so it runs for coach and team too).
   - The preview renders the top 2 objectives by recency (`homeObjectives.slice(0, 2)`) with real `title`/`computeObjectiveProgress(currentCompletions, targetCompletions)`, each card clickable (`onClick → go("objectives")`), plus a "No objectives yet." empty state (also clickable) instead of a blank gap.
2. **Team objectives access (resolved — option (a), read-only, team-scope only; implemented):**
   - Added `team: 'pro'` to `FEATURE_TIER_REQUIREMENTS.objectives` in `paywall.ts`.
   - **Role-string finding, confirmed and resolved — narrower than originally suspected:** the mobile app's domain-level `PaywallRole` already uses `'team'` (not `'team_manager'`), so `canAccess`/`checkFeatureAccess` needed no change beyond the tier entry above (`objectives` isn't in `LAUNCH_ACCESS_BANDS`, so it falls through to the plain tier map either way). The actual mismatch was narrower: `ObjectivesRepository`'s *type signature* said `'team_manager'` where runtime code actually passes `'team'` — fixed for type accuracy in `packages/api/src/ports/objectives-repository.ts` and both implementations (`supabase-objectives-repository.ts`, `rest-objectives-repository.ts`); no behavior change, `tsc --noEmit` now passes where it previously errored once the port type changed without updating the implementations.
   - Added a new migration (`supabase/migrations/20260728120000_objectives_team_tier_access.sql`) adding the matching `objectives`/`team_manager` → `pro` case to `has_feature_access()`. **Important:** based this on the *actual* latest redefinition of that function (`20260722140100_peer_engagement_feature_access.sql`, which already includes STORY-8.3's `peerEngagement` case and others) — not the older `20260717130000_has_feature_access_overrides.sql` migration, which would have silently regressed those later additions. `tests/rbac/story-5.1.test.js`/`story-5.2.test.js` dynamically assert the SQL CASE exactly mirrors `FEATURE_TIER_REQUIREMENTS`, which caught this.
   - Also updated the duplicate `FEATURE_TIER_REQUIREMENTS` copy in `supabase/functions/_shared/rbac.ts` (edge middleware) to keep it in sync — a drift test (`story-5.1.test.js` AC2) checks this explicitly.
   - **No RLS policy change was needed** — confirmed `objectives_coach_select` already scopes a team manager to team-only rows once the tier check passes (verified by reading the policy, not changed).
   - Confirmed `ObjectivesScreen.jsx` still gates create/edit on `isCoach` only — no change needed, added a test locking this in.
3. **Player self-authored objectives (resolved and implemented — players only, not team managers):**
   - New migration `supabase/migrations/20260729120000_player_self_authored_objectives.sql` adds a second, additive `for insert` RLS policy (`objectives_player_self_insert`) allowing `coach_id = auth.uid() AND scope = 'player' AND player_id = auth.uid()` for a `role = 'player'` profile, gated by the same `has_feature_access(auth.uid(), 'objectives')` check as the coach path. Postgres OR's multiple permissive policies for the same command, so the existing `objectives_coach_insert` policy is untouched.
   - No SELECT/UPDATE/DELETE policy changes needed: the existing SELECT policy's `scope = 'player' and player_id = auth.uid()` branch already covers a player viewing their own objectives regardless of who authored them, and UPDATE/DELETE's `coach_id = auth.uid()` check is satisfied since a self-authored row's `coach_id` is the player's own id.
   - `ObjectivesScreen.jsx`: added `isPlayer`/`canCreate = isCoach || isPlayer`. A player gets the same "+ Add Objective" trigger and form as a coach, but the scope toggle and player/team picker are hidden (shown only for `isCoach`) and `handleCreate` hard-codes `scope: 'player', playerId: userId, teamId: null` for a player regardless of component state — so a player cannot submit a team-scoped objective or one assigned to someone else even if the form were tampered with client-side (the RLS policy above is the real backstop either way). Added a one-line explainer in the form ("This objective is for you...") instead of showing fields that don't apply.
   - Renamed `ObjectivesRepository.create`'s parameter from `coachId` to `creatorId` (port + both adapters) — it's no longer always a coach; cosmetic, no behavior change.
   - Added a "· Self-set" suffix to a player's own objective card when `objective.coachId === userId`, so a player can tell their own goals apart from coach-assigned ones.
   - **New open question, not decided — flagged rather than guessed:** should a coach be able to see a player's self-authored objectives? Today's `objectives_coach_select` only grants a coach visibility where `coach_id = auth.uid()`, so a self-authored row (`coach_id` = the player's own id) is invisible to any coach. Built as private-to-the-player for this pass. See Open questions.
   - Team Manager explicitly **not** included in self-authoring — stays read-only per the decision in Fix plan item 2, unchanged by this item.
4. **Suggestions latency — deferred to STORY-11.2, and turns out to have no client-side component here.** The originally-proposed "parallelize `listOwned()` with the team/age lookups via `Promise.all`" doesn't apply: on inspection, the age-range values (`ageMins`/`ageMaxs`) are derived synchronously from the already-loaded `teams` state via `.map()`/`.filter()`, not a separate async call — there's only one async call (`listOwned()`) before `listRecommendations()` in `loadSuggestions`, so there's nothing to parallelize it with. No client-side change made; the actual fix is entirely server-side, owned by STORY-11.2.

## Resolved decisions

- **Team Manager access to Objectives:** yes, read-only, scoped to team-wide (`scope: 'team'`) objectives only — not individual players' objectives. See Fix plan item 2.
- **Access tier/level:** `team: 'pro'`, read-only (matches the tier team managers already pay for `ai`/`viewProgress`; write access was never in scope — AC-1 scopes creation to the coach). See Fix plan item 2.
- **STORY-5.2 reopen:** no — add a new AC-6 to STORY-5.2 once this ships, rather than reopening it.
- **Self-authored objectives — reversed, now in scope (players only):** originally deferred as post-MVP; explicitly un-deferred and built. Scoped to players self-authoring their own player-scoped objectives only — **not** team managers, who stay read-only per the decision above (building both would have contradicted that decision, so this was confirmed explicitly before implementing). See Fix plan item 3.
- **Suggestions latency:** deferred entirely to STORY-11.2 — no separate decision needed here, and turned out to have no independent client-side component anyway.

## Open questions — new, discovered during implementation

- **Should a coach be able to see a player's self-authored objectives?** Built as private-to-the-player for this pass — today's `objectives_coach_select` RLS policy only grants a coach visibility where `coach_id = auth.uid()`, so a self-authored row is invisible to any coach. If coaching oversight requires visibility, this needs a new SELECT policy branch (e.g. via roster/team membership between the coach and the player), which wasn't built here to avoid speculative join logic without a confirmed requirement.
